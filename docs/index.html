hexa-go

hexa-go scaffolds Go services in a hexagonal (ports and adapters) layout and keeps extending them. After the first generate, hexa-go add model writes the model, repository, service, handler and tests, then registers them in main.go and the route table.

Wiring done for you

New code is inserted above marker comments, imports are added without duplicates, and the file is re-formatted. A failed command rolls back every file it touched.

One syntax, one naming scheme

Name:Type[:GormOptions[:Validation]] for fields; order-item becomes OrderItem, order_item.go and /order-items.

Tested end to end

The test suite generates projects and runs go build and go vet on them, so a broken template fails the build.

Quick Start

Requires Go 1.24 or newer.

go install github.com/erwinhermantodev/hexa-go@latest

hexa-go generate my-api --module github.com/me/my-api
cd my-api && go mod tidy

hexa-go add model Product -f "Name:string::required" -f "Price:float64::required,gt=0"

docker-compose up -d postgres
go run main.go
curl localhost:8080/api/v1/health

Architecture

Dependencies point inward. Handlers depend on service interfaces, services on repository interfaces, and main.go is the only place that builds concrete objects.

HTTP handler  →  service  →  repository interface  →  GORM adapter  →  database
(transport)      (core)       (port)                    (adapter)

Use add model for the layered layout (model/, repository/, service/) or add module to keep one feature in one package under internal/modules/.

Commands

CommandDescriptionFlags
generate [name] Create a new project -m, -a, -d, -i, --minimal, --force
add model [name] Model, repository, service, handler and tests -f, --no-repo, --no-service, --no-handler, --force
add module [name] The same pieces co-located in internal/modules/<name> -f, --force
add service [name] Empty service, registered in main.go --force
add handler [name] Empty handler with a Health method --force
Safe by default: commands exit non-zero on error, never overwrite existing files without --force, and can be run twice without duplicating registrations.

Naming Rules

Give a name in any style (order-item, order_item, OrderItem, Order Item). The generator derives the rest:

FormExampleUsed for
PascalOrderItemtypes, NewOrderItemService
camelorderItemvariables in main.go
snakeorder_itemfile names
kebab pluralorder-itemsURL path; Category becomes /categories
packageorderitemmodule package name

A trailing Service or Handler is dropped, and module names that would clash with generated packages (utils, routes, ...) are rejected.

Field Syntax

Name:Type[:GormOptions[:Validation]]

-f "Title:string::required,min=5,max=200"
-f "Slug:string:unique:required"
-f "Published:bool:default=false"
-f "PublishedAt:*time.Time"
SlotMeaning
Typestring, int, uint, int64, float64, bool, time.Time, gorm.DeletedAt, pointers, slices, custom types
GormOptionsseparated by ;; write values with = (default=false becomes default:false)
Validationgo-playground/validator tags separated by ,

ID, CreatedAt, UpdatedAt and DeletedAt are added automatically and are not accepted in create or update requests. Mistakes, such as a GORM option in the validation slot, are reported before any file is written.

How Wiring Works

main.go and routes.go contain marker comments. New code is inserted on the line above a marker and the file is re-formatted with gofmt.

MarkerFileReceives
// [REPOS-INIT]main.goxRepo := repository.NewXRepository(db)
// [SERVICES-INIT]main.goxService := service.NewXService(xRepo)
// [HANDLERS-INIT]main.goxHandler := handler.NewXHandler(...)
// [ROUTER-HANDLERS-INIT]main.gorouter.XHandler = xHandler
// [HANDLER-FIELDS-EXPORTED]routes.gothe XHandler field on Router
// [ROUTES-INIT]routes.gothe route group
Keep the markers. Without them hexa-go add fails and rolls back. Everything else is yours to edit.

Directory Structure

├── main.go // config, database, wiring, server, graceful shutdown
├── model/ // entity, create request, response
├── repository/ // GORM repositories
├── service/ // business logic
├── transport/
│ ├── http/handler/ // Echo handlers
│ ├── http/routes/ // route table, /swagger, /api/v1/health
│ └── grpc/ // skeleton, not started yet
├── internal/modules/ // co-located modules (add module)
├── utils/ // config, database, jwt, password, validator, response
├── configs/, locales/, migrations/, docs/
└── Makefile, Dockerfile, docker-compose.yml, .github/workflows/ci.yml

Configuration

Values come from configs/config.yaml, then environment variables. Every key can be set as APP_<KEY>; these shorter names also work.

VariableDefault
DB_HOST, DB_PORT, DB_USER, DB_PASSWORD, DB_NAMElocalhost, 5432, postgres, postgres, project name
APP_DATABASE_DRIVERpostgres (or mysql, sqlite)
JWT_SECRETyour-secret-key (change it)
SERVER_PORT, GRPC_PORT8080, 9090

.env.example is a reference only; nothing loads a .env file.

Runtime & Deployment

  • Server: Echo with request logging, panic recovery and CORS.
  • Shutdown: on SIGINT or SIGTERM the server stops accepting requests and waits up to 10 seconds for in-flight ones.
  • Docker: multi-stage Dockerfile; docker-compose up -d starts the app and PostgreSQL.
  • CI: a GitHub Actions workflow builds and tests with the Go version from go.mod.
  • Swagger: make swag-init generates the spec; the UI is served at /swagger/index.html.

Known Limitations

Generated apps do not create their tables. Add db.AutoMigrate(...) or use migrations. See ROADMAP.md for the full list.
  • No auth endpoints yet; JWT and bcrypt helpers exist, and the default User service stores passwords as received.
  • Only create requests are validated, not updates.
  • .env is not loaded and log_level is not applied to the logger.
  • gRPC is a skeleton: no .proto files and the server is not started.
